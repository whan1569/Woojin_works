# IOForge 결함 분석·해결·검증 사례집

> 기록 범위: 2026-08-24 ~ 2026-10-15  
> 근거: IOForge 저장소의 코드, 변경 이력, 자동화 테스트와 기존 Woojin_works 개발·현장 기록  
> 상태 구분: **코드 반영 / 자동화 검증 근거 / 실장비 확인 / 원인 미확정**을 서로 구별한다.  
> 공개 범위: 문제 해결 방식과 일반화된 설계 판단만 기록하며, 회사 소유 템플릿·고객 고유 I/O 목록·장비 전체 설정 파일은 공개하지 않는다.

## 1. 이 문서를 작성한 이유

IOForge는 단순히 HW/IO 파일을 생성하는 프로그램으로 끝나지 않는다. 동일한 카드 구성이라도 **물리적 슬롯 순서, Powerlink Node, 모션 드라이브 방식, 기종별 생성 옵션, PLC 프로젝트의 지원 하드웨어, 설치된 런타임 상태**가 맞아야 실제 장비에서 동작한다. 잘못된 출력은 단순한 문법 오류에 그치지 않고 장비에서 모듈이 인식되지 않거나 신호가 의도한 위치에 연결되지 않는 문제로 이어질 수 있다.

따라서 개발 과정에서 발생한 문제를 `증상 → 재현 조건 → 원인 가설과 확인 → 수정 → 회귀 검증 → 실장비 검증 범위`로 남긴다. 현장에서 확인한 사실과 코드만으로 추론할 수 있는 범위를 혼동하지 않는 것이 이 문서의 핵심 원칙이다.

### IOForge의 생성 경로

```text
장비별 실제 카드·모션 구성
       ↓
JSON 기반 프로젝트/표준/템플릿
       ↓
Rack·Slot·Node·Module No. 정합성 검사
       ↓
하나의 프로젝트 모델에서 동시 생성
       ├─ ConfigHW.xml
       ├─ ConfigIO.xml
       └─ IO_info.CSV
       ↓
Automation Studio Build / 실제 HW 등록 / 설치
       ↓
실장비 상태와 진단 화면으로 최종 확인
```

동일 데이터에서 세 파일이 생성된다는 사실만으로 마지막 단계의 성공까지 보장할 수는 없다. 그 경계를 명확하게 다루기 위해 다음 결함을 기록한다.

## 사례 1. X20PS3300: 파일에는 있으나 장비가 인식하지 못한 문제

**시기:** 2026-08-25 ~ 08-27  
**분류:** HW 생성기 보완 + PLC 프로젝트 구성 의존성  
**결과:** 현장 재시험을 통한 정상 인식 기록 존재

### 개발 동기와 증상

신규 카드를 현장 구성 도구에서 선택할 수 있도록 지원한 후, 생성된 HW/IO 파일을 적용했을 때 카드 뒤쪽 모듈은 정상적으로 보이지만 대상 카드만 `not plugged`로 표시되는 현상이 발생했다. 카드 진단의 일련번호·펌웨어·변형 정보도 채워지지 않았다.

버스 자체가 끊어진 현상이라면 뒤쪽 카드도 함께 인식되지 않을 가능성이 있다. 따라서 첫 판단은 **버스 연결이 유지되는 것과 특정 카드가 런타임에서 식별되는 것은 별개의 문제**라는 것이었다.

### 원인 확인 과정

1. 신규 카드가 `ConfigHW.xml`에 실제 경로로 출력되는지 확인했다.
2. `ConfigIO.xml`에서 Module OK와 진단 데이터 채널이 연결되는지 점검했다.
3. Physical View에 동일 카드를 수동으로 배치한 경우와 동적 구성 파일을 사용한 경우를 비교했다.
4. 정상 동작하는 동적 카드의 설정과 대상 카드의 HW 지원 선언을 비교했다.
5. CPU Configuration의 `Additionally supported hardware` 목록에 대상 카드가 빠져 있음을 확인했다.

**확정한 문제:** IOForge의 XML 출력 여부와 별개로, PLC 프로젝트가 동적 생성 대상 하드웨어를 지원 목록에 포함해야 하는데 해당 등록이 누락되어 있었다. 즉 파일 생성 버그만으로 설명할 수 있는 문제가 아니었다.

### 해결 방식

- 카드 모델 및 진단 채널이 출력되도록 HW/IO 생성 규칙을 보완했다.
- CPU 프로젝트에 해당 HW 모델과 버전 지원 정보를 추가했다.
- Clean Configuration, Rebuild, Initial Installation을 통해 장비에 적용했다.
- 현장에서 모듈 식별 상태를 재확인했다.

### 검증 결과와 교훈

기존 개발 기록에는 현장 장비의 정상 인식까지 확인한 것으로 남아 있다. 이를 통해 향후 카드를 신규 지원할 때 `템플릿 존재 → 출력 파일 생성 → 프로젝트의 지원 HW 등록 → 설치 → 실장비 인식` 순서로 확인하는 기준을 마련했다.

**재발 방지 원칙:** XML에 모듈이 존재한다는 사실만으로 HW 지원이 끝났다고 판단하지 않는다.

관련 기록: [`04_개발_진행_기록.md`](04_개발_진행_기록.md) · IOForge 2026-08-25 `X20PS3300` 생성 보완 커밋.

## 사례 2. X20 Powerlink 원격 노드의 물리 순서와 생성 경로 불일치

**시기:** 2026-08-26 ~ 09-01  
**분류:** 데이터 모델과 실제 HW 토폴로지의 의미 불일치  
**결과:** 생성기 및 자동화 테스트 보완

### 증상과 문제 정의

초기 구성에서는 화면상 카드의 `slot` 번호를 그대로 하드웨어의 ST 경로에 적용하거나, Powerlink 노드의 필수 버스 컨트롤러를 사용자 데이터와 별개로 암묵적으로 처리하는 구간이 있었다. 그 결과 **카드 배열의 논리적 번호와 실제 출력되는 물리 경로의 의미**가 어긋날 수 있었다.

여기서 핵심은 사용자가 화면에서 배열을 편집하는 순서와 B&R HW 구성에 삽입되는 경로 순서가 항상 동일하다고 가정하면 안 된다는 점이었다.

### 분석 및 해결

- Rack별로 모듈을 물리 슬롯 기준으로 정렬한 뒤 출력하도록 생성 경로를 정리했다.
- CPU 로컬 I/O와 Powerlink 원격 I/O의 경로 처리 규칙을 분리했다.
- 원격 노드의 버스 컨트롤러(`X20BC0083`)를 생성 결과에 명시하도록 수정했다.
- 노드의 필수 전원 모듈(`X20PS9400`)을 함께 고정 배치해 사용자가 실수로 이동시키거나 선행 슬롯에 카드를 삽입하지 못하도록 했다.
- 기존에 필수 카드가 저장되지 않은 프로젝트를 열면 누락분을 보정하도록 했다.

특히 **Rack의 내부 식별자와 Node 주소를 분리**했다. `node_주소`와 같은 문자열을 객체 ID로 쓰면 주소 변경이나 중복 구성이 화면 객체의 동일성을 흔들 수 있다. 그래서 내부 Rack ID는 고유하게 유지하고, 물리 Node 주소는 독립 속성으로 관리하도록 바꿨다.

### 기술적으로 중요한 결정

```text
내부 객체 ID: 편집·저장 과정에서 같은 랙을 식별하기 위한 값
물리 Node 주소: 현장 Powerlink 주소에 대응하는 값
물리 슬롯: 실제 장착 및 출력 경로를 결정하는 값
Module No.: 진단 배열과 채널 참조에 사용하는 일련번호
```

이 네 개를 같은 개념으로 취급하지 않도록 분리했다.

### 검증 범위

생성기 테스트에서 원격 노드의 컨트롤러, 필수 구성 계층, 카드 순서에 따른 출력 경로를 확인하는 조건이 추가됐다. 자동화 생성 결과가 정합성을 갖추도록 개선했지만, 이 테스트만으로 모든 현장 배선 및 장착 상태를 입증하는 것은 아니다.

**재발 방지 원칙:** 내부 데이터 저장 순서가 아니라 실제 HW 토폴로지에 맞는 출력 규칙으로 생성한다.

관련 커밋: `6e607e9c6`(물리 순서 생성), `1a0490faa`(Rack ID 분리), `cc62f242e`(필수 컨트롤러 표시).

## 사례 3. Module No. 1번 시작으로 발생한 번호 체계 불일치

**시기:** 2026-09-01 ~ 09-02  
**분류:** 0-based / 1-based 경계 오류  
**결과:** 번호 정렬 로직 수정 및 실제 출력 매핑 확인

### 개발 동기

현장 담당자가 카드 추가·삭제·이동 후 Module No.를 일일이 다시 입력하면 누락·중복 또는 채널 참조 불일치가 발생하기 쉽다. 이를 줄이기 위해 물리적 Rack·Slot 순서에 따른 자동 정렬 기능을 만들었다.

### 발견된 결함

최초 정렬 구현은 Module No.를 **1번부터** 증가시켰다. 그러나 실제 생성물에서 참조하는 진단 번호 체계는 **0번부터** 시작하는 기준이어서 번호와 맵핑 위치가 한 칸씩 밀리는 위험이 있었다.

### 해결 과정

1. 자동 정렬의 초기값을 `1`에서 `0`으로 수정했다.
2. 빈 구성에서 다음 번호를 계산할 때 기본 최대값을 `0`이 아닌 `-1`로 설정했다. 그러면 `max + 1`이 자연스럽게 `0`이 된다.
3. 생성 파일의 모듈 배열 및 채널 참조가 실제 카드 순서와 일치하는지 대조했다.
4. 신규 노드 생성과 기존 노드 정렬 모두 동일한 번호 정책을 적용했다.

### 결과

기존 기록에는 0번부터 재정렬한 구성에서 각 슬롯의 채널이 의도한 위치에 대응하는 것을 확인했다고 남아 있다. 이후 입력 과정에서 번호 체계를 일관되게 적용할 수 있게 됐다.

**교훈:** 자동 정렬이 '숫자를 보기 좋게 만드는 기능'에 그쳐서는 안 된다. 생성되는 I/O 연결이 어떤 인덱스 계약을 따르는지까지 검증해야 한다.

관련 커밋: `a4b60044b`(2026-09-02).

## 사례 4. KEB 구성에서 서로 다른 PDO 계약이 섞인 문제

**시기:** 2026-09-01  
**분류:** 모션 장치의 데이터 계약(PDO) 혼용  
**결과:** 검증된 속도 제어용 PDO와 I/O 연결 복원, 회귀 테스트 추가

### 증상과 근본 문제

KEB 드라이브를 생성할 때 기존 X20용 템플릿의 일부 데이터 항목은 위치 제어 중심으로 작성되어 있었으나, 실제 사용 목적은 펌프 속도 제어였다. 다른 템플릿에 정상적으로 쓰이던 속도 PDO가 존재했지만, 두 계약이 섞이면 XML이 형식적으로 유효하더라도 **실제 프로그램이 읽고 쓰려는 데이터와 드라이브 PDO의 의미가 다를 수 있다.**

### 문제를 좁힌 방법

- 생성한 HW와 IO 양쪽에 동일한 PDO 포인트가 존재하는지 비교했다.
- 위치 제어 성격의 불필요한 PDO가 포함되어 있는지 점검했다.
- 다른 계열에서 현장 사용 근거가 있는 속도 PDO 세트를 기준으로 삼았다.
- 애플리케이션 변수 이름을 임의로 만들어 연결하는 방식은 피했다.

### 해결 방식

속도 제어와 직접 관련된 `RelativeLoad`, `ElectricalOutputPower`, `Controlword`, `Statusword`, `VelocityActual`, `TargetVelocity` 데이터 계약으로 정리했다. IO 쪽은 사용 근거가 있는 펌프 제어 링크를 그대로 유지하고, 추정에 의존한 변수명 치환을 제거했다.

**수정의 핵심:** 템플릿 이름이 KEB라고 해서 상호 대체 가능한 것이 아니다. PDO의 의미와 실제 제어 변수의 계약이 맞는지 확인해야 한다.

### 결과와 확인 범위

회귀 테스트에는 필수 속도 PDO의 존재와 잘못 포함된 위치 제어 PDO의 부재를 확인하는 검사가 추가됐다. 기존 업무 기록에는 일부 축에서 생성 결과와 인스턴스 구성이 확인된 내역도 있다. 여기서 입증된 것은 **해당 생성 결과의 계약 일치성**이며, 모든 조합의 실제 구동 성공을 포괄적으로 주장하지 않는다.

관련 커밋: `e4801395c`, `938f82518`, `27ba4cbbb`.

## 사례 5. 구형 Standard/프로젝트를 불러오면서 생성 옵션이 유실되는 문제

**시기:** 2026-09-14 ~ 10-06  
**분류:** 데이터 모델 진화와 하위 호환성  
**결과:** 이전 형식 변환, 프로젝트 레벨 정책 보존, 기존 사용자 파일 마이그레이션

### 왜 발생했는가

초기에는 기존 프로그램의 설정을 재현하기 위해 `tag1`, `servo_pump` 같은 **프로젝트 전체에 영향을 주는 플래그**를 모션마다 복제하여 보관하는 단계가 있었다. 하지만 이 속성은 모션 하나의 물리적 특성이 아니라 출력 생성 방법을 선택하는 정책이다. 서로 다른 축이 들어가거나 프로젝트 구조가 업데이트되면 모션별 복제 값과 실제 프로젝트 설정이 어긋날 가능성이 있었다.

또한 초기 버전에서 사용하던 `page1`~`page8` 형식의 파일은 최신 프로젝트 JSON 구조와 다르기 때문에, 파일을 읽을 수 있더라도 변환 단계가 없으면 그대로 사용하기 어려웠다.

### 분석 순서

1. 기존 페이지 형식에서 옵션 값이 어느 위치에 저장되는지 확인했다.
2. 최신 데이터 모델에서 프로젝트와 모션이 각각 책임져야 할 설정을 분류했다.
3. 저장·불러오기 과정에서 플래그가 사라지거나 기본값으로 바뀌는 경로를 추적했다.
4. 기존 사용자 표준을 무조건 덮어쓰지 않고 필요한 속성만 이식할 수 있는지 검토했다.

### 해결 방식

- 구형 페이지 기반 프로젝트(`page1`~`page8`) 입력을 판별해 최신 모델로 변환하는 경로를 추가했다.
- 전체 생성 옵션은 `project` 수준에 저장하고, 모션에는 실제 장치 종류 및 축 속성만 남겼다.
- 옛 파일을 읽을 때 모션에 남아 있던 구형 옵션 값도 인식해 프로젝트의 기본값으로 복구할 수 있게 했다.
- 기본 제공 표준이 갱신됐더라도 사용자가 수정한 기존 표준 전체는 덮어쓰지 않고, 누락된 생성 옵션만 보충하도록 했다.
- 변환 시 기존 파일의 변경 전 백업을 남기는 안전장치를 사용했다.

### 기술적 판단: 호환성 유지와 정책 수정은 별개

구형 데이터의 `servo_pump` 값은 읽을 수 있도록 보존했지만, 후속 Broadcast 생성 판정에서는 **현재 실제 모션 상태**를 우선 기준으로 바꿨다. 과거 데이터를 해석할 수 있어야 한다는 것과 과거 결함 있는 조건식을 계속 적용해야 한다는 것은 서로 다른 요구다.

### 검증 결과

프로젝트 플래그 저장/복원, 이전 모션 필드 무시, 구형 표준 생성, 기본 제공 표준의 옵션 보충을 검사하는 테스트가 추가됐다. 또한 구형 파일을 읽을 때의 형식 감지와 변환 호출은 현재 소스에 존재한다. **코드·테스트 경로 확인**과 **실제 고객 파일 전체의 이관 완료**는 구분해야 한다.

관련 커밋: `627c0893f`, `6e9d2d00c`, `445e2f7fa`, `627fd2bfd`.

## 사례 6. B&R 모션의 Broadcast 채널 누락 및 잘못된 삽입

**시기:** 2026-10-06  
**분류:** 기능 조건과 레거시 설정 플래그의 결합 오류  
**결과:** 현재 모션 기준 생성 규칙 확정, 양방향 회귀 테스트 추가

### 현상

B&R 모션을 실제로 구성했는데도 옛 `servo_pump` 생성 옵션이 꺼져 있으면 Broadcast 채널이 생성되지 않을 수 있었다. 반대로 과거 플래그만 남아 있으면 B&R 모션이 없는 프로젝트에 Broadcast 구성이 추가될 수 있었다.

### 수정 이력을 통한 원인 분석

처음 조건은 다음과 같은 구조였다.

```python
# 이해를 돕기 위한 단순화된 예시 (제품 소스 원문 아님)
if legacy_servo_pump_flag:
    add_broadcast_channel()
```

이 조건은 **사용자가 지금 무엇을 구성했는지**보다 **과거 파일의 옵션 상태**에 의존한다. 누락 증상을 우선 막기 위해 한때 `has_br or legacy_servo_pump_flag` 방식도 도입했지만, 이 방법은 B&R 모션이 없는 구성에 채널을 삽입하는 문제를 완전히 제거하지 못한다.

최종적으로 다음 판단으로 정리했다.

```python
# 개념 표현용 의사 코드
has_br = any(motion.family == "B&R" for motion in project.motions)
if has_br:
    add_broadcast_channel()
else:
    omit_broadcast_channel()
```

즉 **설정 플래그가 아니라 현재 장치 구성 자체를 진실의 원천(source of truth)으로 삼았다.**

### 검증 시나리오

| 실제 모션 | 구형 옵션 플래그 | 기대 생성 결과 |
| --- | --- | --- |
| B&R 존재 | 켜짐 | Broadcast 생성 |
| B&R 존재 | 꺼짐 | Broadcast 생성 |
| B&R 없음 | 켜짐 | Broadcast 생성하지 않음 |
| B&R 없음 | 꺼짐 | Broadcast 생성하지 않음 |

이 네 조건 가운데 문제가 된 양쪽 경계(모션 있음·플래그 꺼짐, 모션 없음·플래그 켜짐)를 모두 검사하도록 회귀 테스트가 변경됐다.

### 결과

`ConfigurationGenerator.generate()`는 현재 B&R 모션 존재 여부를 기준으로 Broadcast 템플릿을 삽입한다. 이는 저장소 코드와 테스트에서 확인된다. 단, 이를 모든 장비의 현장 재설치·재구동 완료로 표현하지 않는다.

**핵심 교훈:** 임시 우회 조건(`A or B`)이 한쪽 누락은 해결해도 반대쪽 오동작을 만들 수 있다. 결정 조건을 실제 도메인 상태로 재정의하는 것이 근본 해결이다.

관련 커밋: `da7e248f9`(중간 수정), `4778cf707`(최종 조건 변경), `2bf501648`(테스트 조건 확정).

## 사례 7. 기존 사용자 Standard와 신규 내장 Standard 사이의 설정 불일치

**시기:** 2026-09-14 ~ 10-06  
**분류:** 사용자 데이터 보존과 기본 데이터 배포 정책  
**결과:** 새 기본값 보충 + 선택적 필드 마이그레이션

### 문제의 성격

IOForge는 배포할 때 기본 Standard를 포함하지만, 현장 담당자는 설치 후 자신이 사용하는 Standard를 수정한다. 업데이트 시 내장 Standard 전체를 복사해 덮어쓰면 사용자 변경이 사라지고, 반대로 기존 파일을 전혀 건드리지 않으면 새 버전에서 필수 생성 옵션이 빠진 상태가 남을 수 있다.

### 개선 과정

- 신규 Standard가 아직 없는 경우에만 기본 파일을 추가한다.
- 같은 이름의 사용자 Standard가 있으면 파일 전체를 덮어쓰지 않는다.
- 이전 형식에서 누락된 특정 생성 옵션은 기존 모션 값 또는 대응되는 내장 Standard를 기준으로 보완한다.
- 이 변경은 원자적 저장 및 변경 전 백업 경로를 사용한다.
- 기존 모션 객체에 남아 있는 폐기 예정 옵션 필드는 정규화한다.

### 결과와 시사점

업데이트와 사용자 작업물 보호라는 서로 충돌하는 요구를 필드 수준의 이관으로 나눴다. 설정 변경의 범위를 좁혀 **새 소프트웨어의 생성 일관성과 사용자 데이터의 소유권을 함께 유지**하도록 설계했다.

관련 커밋: `29550fe16`, `445e2f7fa`.

## 사례 8. 구버전 Python 환경에서 XML 출력이 실패한 문제

**시기:** 2026-08-25  
**분류:** 개발 환경과 배포 환경의 API 호환성  
**결과:** 하위 호환 파일 쓰기 API로 변경, 전체 표준 출력 테스트 추가

### 현상 및 원인

개발 환경에서는 사용 가능했던 파일 출력 호출의 일부 인자가, 현장에서 실행 파일을 빌드하는 이전 Python 버전에서는 지원되지 않아 XML 생성 실패 가능성이 있었다. 특히 `Path.write_text(..., newline=...)` 호출의 호환성이 문제가 됐다.

### 해결과 검증

`Path.open("w", encoding="utf-8", newline="\n")`으로 파일 스트림을 열어 출력하도록 변경해 버전 의존성을 줄였다. 이후 전체 제공 Standard를 순회하며 세 산출물이 존재하고 비어 있지 않은지, XML을 파싱할 수 있는지, 잘못된 개행이 들어가지 않는지를 검사하는 회귀 테스트를 추가했다.

**핵심 교훈:** 개발 PC에서의 정상 실행은 현장 배포본의 성공을 보장하지 않는다. 설치·빌드 환경 차이를 입출력 계층까지 고려해야 한다.

관련 커밋: `8b4dbddcc`.

## 사례 9. 관리자 화면에서 사용 중인 카드·신호가 표시되지 않는 문제

**시기:** 2026-08-28  
**분류:** 사용자 작업 상태와 표시 기준의 불일치  
**결과:** 저장 여부와 무관하게 현재 편집 중인 구성 기준으로 표시

초기 하이라이트 기능은 사용자가 이미 저장한 Standard를 선택한 경우에만 사용 중인 카드·신호를 표시했다. 하지만 현장 작업의 대부분은 새 프로젝트를 편집하는 중에 일어난다. 저장되지 않았다는 이유로 현재 사용 중인 카드·신호가 보이지 않는 것은 기능의 목적과 맞지 않았다.

표시 기준을 `선택된 저장 Standard`에서 **현재 편집 중인 프로젝트 모델**로 변경해, 새 구성에서도 사용 카드·신호가 표시되도록 수정했다. 이는 데이터 오류라기보다 작업 흐름을 기준으로 화면의 참조 대상을 바로잡은 사례다.

이 사례는 **생성 파일 동일성**, **프로젝트 설정 동일성**, **장비에 설치된 상태 동일성**이 서로 다른 검증 대상이라는 점을 보여준다.

## 4. 개발자로서 도출한 공통 원칙

1. **파일 생성과 장비 인식은 별개:** XML이 유효해도 프로젝트의 지원 HW와 실제 설치 상태가 틀리면 동작하지 않을 수 있다.
2. **논리 ID와 물리 주소를 분리:** 프로그램 내부 객체의 정체성과 현장 HW의 위치를 같은 필드로 관리하지 않는다.
3. **데이터 계약을 기준으로 검증:** 드라이브 모델명이 아니라 실제 PDO와 제어 변수의 의미가 맞는지 확인한다.
4. **진실의 원천을 현재 상태로 설정:** 과거 플래그보다 지금 구성된 모션·카드 상태를 우선한다.
5. **기존 사용자 데이터를 보존:** 업그레이드 과정에서는 전체 파일 덮어쓰기보다 의미가 검증된 항목만 마이그레이션한다.
6. **회귀 조건은 양방향으로 작성:** '반드시 생성'뿐 아니라 '생성하면 안 되는 경우'도 검사한다.
7. **검증 수준을 나눠 기록:** 코드 반영, 자동화 테스트, AS Build, 장비 인식, 실제 동작 검증을 같은 말로 표현하지 않는다.
