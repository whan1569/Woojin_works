# IOForge 적용 기술과 설계 접근

## 1. Local-First Architecture

IOForge는 인터넷과 중앙 서버 없이 모든 핵심 작업을 수행한다. 서버 연결은 공유가 필요할 때만 사용하며, 서버 장애가 프로젝트 편집·저장·파일 생성에 영향을 주지 않는다.

이는 단순 데스크톱 구현이 아니라 연결 상태보다 작업 지속성이 중요한 생산 현장을 고려한 아키텍처 선택이다.

## 2. Progressive Standardization

초기부터 모든 현장 구성을 중앙 표준에 맞추지 않고 실제 프로젝트를 먼저 축적한다.

```text
현장별 자유 구성
→ 프로젝트 데이터 축적
→ 반복 패턴 확인
→ 기술 검증
→ Standard 승격
```

표준화를 포기한 것이 아니라, 충분한 현장 근거가 확보된 이후로 표준화 시점을 조정한 Bottom-up Standardization 접근이다.

## 3. Model-Driven Engineering

사용자가 구성한 프로젝트 모델을 기준으로 `ConfigHW.xml`, `ConfigIO.xml`, `IO_info.csv`와 프로젝트 JSON을 생성한다. 사람이 각 파일을 개별 작성하지 않고 구조화된 모델에서 실행 설정과 확인 문서를 함께 생성한다.

## 4. Single Source of Truth

카드 모델, 슬롯, 채널, 변수명과 신호 정의를 동일한 데이터 기준으로 화면·검증·산출물 생성에 사용한다. 한 정보를 여러 파일에 반복 입력하면서 발생하는 불일치를 줄인다.

단일 기준 데이터가 틀리면 모든 결과에 영향을 줄 수 있으므로 Admin 역할과 입력 검증을 함께 적용한다.

## 5. Metadata-Driven Design

카드·신호·Standard와 템플릿을 프로그램 코드에서 분리해 JSON으로 관리한다. 새로운 카드나 신호를 지원할 때 핵심 코드를 수정하는 대신 관리 데이터와 템플릿을 확장할 수 있다.

향후 카드 메타데이터는 다음 항목까지 포함하도록 확장한다.

- HW Upgrade 버전
- Additional Hardware 등록 필요 여부
- 기본 파라미터
- 필수 Bus Module과 Terminal Block
- 지원 컨트롤러와 Automation Studio 버전

## 6. Template-Based Generation

컨트롤러·카드별 HW/IO 템플릿을 분리하고 프로젝트의 경로·슬롯·모듈 번호를 적용해 XML을 생성한다.

- 카드별 XML 차이 격리
- 검증된 기존 형식 재사용
- 신규 카드 추가 시 영향 범위 축소
- 컨트롤러별 형식 차이 대응

## 7. Layered Architecture

| 계층 | 책임 |
|---|---|
| UI | 카드·Rack·채널 편집 |
| Domain | 모델과 구성 규칙 |
| Store | JSON 저장·백업·호환 처리 |
| Generator | XML·CSV 생성 |
| Service | 공유 저장소 Push/Pull |
| Admin | 카드·신호·Standard 관리 |

역할별 책임을 분리해 일반 프로그램과 Admin이 동일한 데이터·생성·전송 로직을 공유한다.

## 8. Domain Modeling

Automation Studio의 복잡한 내부 화면을 그대로 복제하지 않고 현장 업무 단위로 추상화했다.

```text
Project
→ Controller
→ Powerlink Node
→ Rack
→ Slot
→ Module
→ Channel
→ Signal
```

이를 통해 사용자는 XML 경로나 내부 객체 구조보다 실제 카드 배치와 채널을 중심으로 작업한다.

## 9. Direct Manipulation Interface

카드 Drag & Drop, 슬롯 사이 삽입, 위·아래 이동과 채널 테이블 편집을 적용했다. 사용자가 최종 구조를 보면서 직접 조작하는 방식으로 기존 카드 추가와 채널 관리의 인지 부담을 줄였다.

## 10. Preflight Validation

파일 생성 전 다음 구성 오류를 검사한다.

- Node·Station·Module 번호 충돌
- 필수 카드·템플릿 누락
- 카드 데이터 필수 필드
- 기본 전원모듈 보호
- Standard에서 사용 중인 카드·신호 추적

향후에는 사용 카드와 Additional Hardware 선언, HW Upgrade 버전과 필수 액세서리 조합까지 사전 검사한다.

## 11. Atomic File Operation

관리 데이터와 서버 파일을 직접 덮어쓰지 않고 임시 파일을 완전히 기록한 뒤 원본과 교체한다. 저장이나 전송 도중 중단돼도 기존 정상 파일이 중간 상태로 손상될 가능성을 줄였다.

## 12. Backup and Append-Only Versioning

- 관리 데이터 변경 전 자동 백업
- 일반 프로젝트는 프로젝트별 최신본 유지
- Standard는 사용자·시간별 이력 누적
- Pull한 Standard는 서버 원본과 분리된 로컬 편집본으로 관리

데이터 성격에 따라 Snapshot과 Append-Only 전략을 구분해 불필요한 파일 증식과 이력 손실을 함께 방지한다.

## 13. Explicit Synchronization Boundary

공유 저장소는 자동 동기화가 아니라 명시적인 Push/Pull 방식이다.

```text
로컬 작업 → Push → 공유 저장소
공유 저장소 → Pull → 로컬 작업
```

사용자가 서버 반영 시점을 통제하고, 네트워크 단절·자동 충돌·서버 직접 편집이 로컬 작업에 영향을 주지 않도록 했다.

## 14. Role-Based Capability Separation

일반 사용자는 검증된 데이터를 이용해 구성하고, Admin은 카드·신호·템플릿·Standard를 관리한다. 인증 중심 RBAC보다는 사용자 역할에 따라 가능한 작업을 제한하는 Capability Separation에 가깝다.

## 15. Human-in-the-Loop

Push 대상, 덮어쓰기, Standard 교체와 현장 예외 구성을 사용자가 최종 판단한다. 안전성과 예외 대응이 중요한 현장에서 완전 자동화보다 사람의 결정권을 유지한다.

## 16. Backward Compatibility

기존 Standard 형식을 신규 모델로 변환하고, 기본 배포 데이터와 운영 데이터를 분리해 프로그램 교체 후에도 기존 자료를 활용할 수 있도록 했다.

## 17. Regression Testing

ConfigHW·ConfigIO 생성, 카드 경로와 슬롯, ModuleOk Mapping, 공유 저장소와 Standard 이력 등 핵심 규칙을 자동 테스트해 변경에 따른 회귀를 방지한다.

## 18. 구현 기술

| 기술 | 적용 영역 |
|---|---|
| Python | 도메인·저장·생성·서비스 로직 |
| PySide6/Qt | 데스크톱 UI와 Drag & Drop |
| JSON | 카드·신호·Standard·프로젝트 데이터 |
| XML | Automation Runtime HW·IO 구성 |
| CSV | 현장 확인·이관용 IO 목록 |
| UNC File Share | 사내 공유 저장소 |
| Git | 소스·기본 데이터·문서 형상 관리 |
| unittest | 생성·저장·전송 회귀 검증 |

## 설계 요약

> IOForge는 Local-First Architecture와 Model-Driven Engineering을 기반으로 B&R IO 구성을 메타데이터와 템플릿으로 생성·검증하는 사내 데스크톱 엔지니어링 도구다. 점진적 표준화, 사용자 정의형 확장, 명시적 Push/Pull과 원자적 파일 처리를 적용해 현장의 자유도와 작업 지속성을 유지하면서 향후 데이터 기반 표준 관리로 발전할 수 있도록 설계했다.
