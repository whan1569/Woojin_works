# IOForge 설계 의사결정과 품질 확보 방식

> 작성 목적: '어떤 기능을 만들었는가'에서 나아가, 실제 현장 제약 안에서 **왜 이 구조를 선택했으며 변경 후 무엇을 검증했는가**를 정리한다. 기존 설계 기록의 반복보다는 개발 과정에서 드러난 판단 기준을 중심으로 썼다.

## 1. 개발 목적을 다시 정의한 계기

반복적인 HW/IO 구성 업무는 표면상 카드 배치와 채널 연결을 수정하는 작업이다. 그러나 현장에서는 생산 일정, 원격 지원 지연, Automation Studio 사용 난도, 기종별 예외, 과거 프로젝트의 복제 사용이 함께 작용한다. 담당자가 잘못된 카드 경로 하나를 놓치면 XML을 다시 생성하고 빌드하고 설치하는 전체 과정을 되풀이해야 할 수 있다.

이 작업을 줄이기 위해 단순히 화면 입력을 자동화하는 대신 **장비 모델·검증·세 산출물 생성을 하나의 일관된 작업 단위**로 묶었다.

### 초기 문제를 도메인 요구로 옮기는 과정

| 현장 문제 | 소프트웨어 요구 | 구현상의 경계 |
| --- | --- | --- |
| 카드·채널 정보를 여러 파일에 중복 입력 | 단일 프로젝트 데이터 모델 | XML/CSV 생성 규칙은 한곳에 둠 |
| 현장별 특수 카드·옵션이 잦음 | 편집 가능한 카드/신호/표준 데이터 | 일반 사용자와 관리자 권한 분리 |
| 숙련자가 아니면 HW 구성이 어려움 | Rack/Slot Drag & Drop 및 검증 | Automation Studio 전체를 대체하지 않음 |
| 현장 PC가 늘 온라인인 것은 아님 | 로컬에서 완전 동작 | 공유는 명시적 Push/Pull로 분리 |
| 이전 장비 구성의 재사용 필요 | Standard와 구형 파일 호환 | 생성 옵션과 사용자 데이터 보존 |
| 신규 카드 추가 후 뜻밖의 미인식 | 단계별 검증·진단 | XML 유효성만으로 완료 처리 금지 |

개발 초기의 가장 중요한 선택은 '모든 구성을 중앙에서 통제하는 시스템'이 아니라 **현장의 예외를 빠르게 표현할 수 있는 로컬 구성 도구**로 범위를 정한 것이었다. 표준화는 프로그램 사용 이전의 절대 조건이 아니라, 실제 현장 프로젝트를 축적·검증하며 발전시키는 대상으로 보았다.

## 2. 설계 원칙: 표현 모델과 실제 장비를 분리하되 끝까지 연결한다

```text
[관리자가 유지하는 기준 데이터]
카드 모델 / 채널 타입 / 생성 템플릿 / 장비별 Standard
                           ↓
[일반 사용자가 편집하는 개별 프로젝트]
Rack / Node / Slot / Module No. / Motion / 채널 신호
                           ↓
[검증 계층]
식별자 중복, 위치 충돌, 누락된 정의, 생성 조건 확인
                           ↓
[출력 생성 계층]
HW XML + IO XML + 진단용 CSV
                           ↓
[외부 운영환경]
Automation Studio Build → PLC 설치 → 장비 진단
```

이 구조는 파일 단위의 우연한 일치를 줄인다. 다만 외부 운영환경까지 일치한다고 가정하지 않기 위해 자동화 검증과 실장비 검증을 구분한다.

### 단일 생성 모델의 이점

기존 파일을 각각 수정하면 `HW 카드가 있다고 기록됐지만 IO 채널은 다른 카드로 연결`되는 종류의 오류가 생길 수 있다. 단일 프로젝트 모델에서는 카드 정의와 채널 연결을 하나의 객체 그래프로 관리하고, 각각 다른 출력 포맷으로 투영(projection)한다. 따라서 검증도 **출력 파일끼리의 단순 문자열 비교**를 넘어 '한 프로젝트에서 파생된 파일들이 서로 같은 물리 구조를 가리키는가'에 집중할 수 있다.

### 그러나 단일 모델에도 한계가 있다

프로젝트 모델과 생성기 둘 다 같은 잘못된 가정을 하고 있다면 출력 세 파일이 서로 일치하더라도 실제 장비 기준과는 틀릴 수 있다. 실제로 Powerlink 슬롯 순서, 번호 시작점, 지원 하드웨어 등록 문제에서 그런 한계가 드러났다. 그러므로 프로젝트 데이터 자체의 진실성을 검증할 독립 기준으로 **실제 카드 배열, B&R 프로젝트의 Physical Configuration, System Diagnostics**가 필요하다.

## 3. 가장 중요한 기술적 설계 선택

### 3.1 객체 식별자와 물리 주소의 분리

작업 화면에서 Rack을 식별하기 위한 ID는 사용자가 Node 주소를 수정해도 유지되어야 한다. 반면 물리 Node 주소는 장비의 통신 주소를 뜻하므로 바뀔 수 있다. 처음 둘을 결합한 설계는 주소 수정과 중복 구성에서 오류 위험을 만들었다.

이를 해결하기 위해 객체의 내부 ID와 물리 주소를 분리했다. 내부 ID는 UI·저장의 연속성을 위해 고유하게 유지하고, 물리 주소는 별도의 검증 대상이 되도록 했다. 이 선택은 이후 카드 이동과 레거시 프로젝트 불러오기 동작에서도 안정성을 높인다.

### 3.2 모션 상태와 출력 정책의 분리

B&R, KEB, KEBA 같은 모션 구성은 **현재 물리적 제어 대상**을 설명한다. `tag1`이나 과거 `servo_pump` 같은 플래그는 **어떤 형식의 설정 파일을 생성할지**에 관한 정책이다. 이 둘을 혼합하면 오래된 파일에 남은 플래그가 현재 장비와 맞지 않는 출력을 유발한다.

따라서 레거시 플래그는 데이터를 읽고 해석하기 위한 호환성 정보로 관리하되, B&R Broadcast 삽입 여부와 같이 실제 장치 상태로 결정 가능한 출력 조건은 현재 모션 목록에서 계산한다. 이 과정에서 필요 조건뿐 아니라 금지 조건도 회귀 테스트에 포함했다.

### 3.3 알려진 계약을 우선하고 추정으로 매핑하지 않기

KEB 문제에서는 이름이 비슷한 PDO나 프로그램 변수라고 해서 대응 관계를 만들어낼 수 없었다. 장치의 PDO 의미와 소프트웨어가 실제 사용하는 애플리케이션 계약이 맞아야 한다. 따라서 검증된 속도 PDO 세트 및 기존에 동작 근거가 있는 IO 연결을 우선했고, 확인하지 못한 변수로의 임의 치환은 제거했다.

이는 '일단 XML을 생성하는 것'보다 '의도한 제어 의미를 보존하는 것'을 우선하는 판단이었다.

### 3.4 사용자 소유 Standard와 기본 제공 Standard를 다르게 취급

프로그램 배포자가 관리하는 기본 표준을 업데이트하는 것과 현장 담당자가 수정한 작업물을 업데이트하는 것은 동일한 파일 처리 문제가 아니다. 설치 시 사용자 표준을 일괄 덮어쓰면 현장 예외가 사라지고, 아무것도 갱신하지 않으면 신규 필수 플래그가 누락된다.

따라서 신규 파일은 보충하고 기존 파일은 보존하되, 구 버전에 없던 필수 생성 옵션만 명시적으로 마이그레이션하는 절충안을 선택했다. 변경 전 백업·원자적 저장을 사용해 업데이트 과정에서 손상 가능성을 줄였다.

### 3.5 로컬 우선 설계와 공유 기능의 분리

중앙 서버에 항상 접속해야 구성 작업을 할 수 있는 구조는 공장·외근 환경에서 실패 지점을 늘릴 수 있다. 프로젝트 생성과 검증은 로컬에서 완료할 수 있게 두고, 공유 저장소는 사용자가 명시적으로 업로드/다운로드할 때만 동작하도록 설계했다.

프로젝트는 최신 공유본, Standard는 변경 이력이 필요한 정책으로 구분했다. 이는 연결 장애 시에도 현장 작업을 계속할 수 있고, 표준이 언제 어떻게 바뀌었는지를 관리할 수 있도록 한 선택이다.

## 4. 테스트를 단순 '실행 성공'에서 확장한 과정

### 4.1 형식 검증

- 제공 Standard마다 `ConfigHW.xml`, `ConfigIO.xml`, `IO_info.CSV`가 생성되는지 확인
- 두 XML이 파서로 해석되는지 확인
- 치환되지 않은 템플릿 토큰이 남지 않는지 생성 단계에서 검사
- 줄바꿈 등 파일 포맷이 예상한 형식인지 확인

### 4.2 의미 검증

- 원격 노드의 버스 컨트롤러와 카드 경로가 물리 순서와 맞는지 확인
- Module No.와 채널 연결의 참조가 일치하는지 확인
- KEB에서 필요한 속도 PDO가 있고, 잘못된 위치 PDO가 없는지 확인
- 실제 B&R 모션이 있는 경우 Broadcast가 생성되는지 확인
- B&R 모션이 없을 때 오래된 옵션 값만으로 Broadcast가 삽입되지 않는지 확인

### 4.3 호환성 검증

- 기존 프로젝트 JSON/페이지 기반 입력을 해석하는지 확인
- 프로젝트 생성 플래그가 저장과 재로드 후 유지되는지 확인
- 오래된 모션 단위 플래그가 최신 직렬화 결과에 다시 들어가지 않는지 확인
- 신규 내장 Standard를 보충할 때 사용자 표준의 내용을 임의로 덮어쓰지 않는지 확인

### 4.4 현장 적용 검증

위 테스트들은 '생성 소프트웨어가 해당 규칙대로 동작한다'는 근거다. 실제 동작 확인에는 별도의 단계가 필요하다.

| 검증 단계 | 확인 내용 | 통과했다고 말할 수 있는 범위 |
| --- | --- | --- |
| Python 단위 테스트 | 생성기·데이터 모델·출력 계약 | 코드 규칙에 맞게 동작 |
| XML/CSV 검사 | 구조, 파일 존재, 참조 일관성 | 산출물의 정적 정합성 |
| Automation Studio Build | 프로젝트의 형식·의존성 검증 | 해당 개발 환경에서 빌드됨 |
| 장비 설치 및 System Diagnostics | 실제 모듈과 통신·식별 상태 | 해당 장비 구성에서 인식됨 |
| 수동·자동 시퀀스 확인 | 실제 액추에이터 및 조건 동작 | 특정 시험 조건에서 동작함 |

**하위 단계 통과를 상위 단계 통과로 확대 해석하지 않는 것**이 현장 엔지니어링의 품질 기준이다.

## 5. 결함을 해결하는 작업 순서의 변화

초기에는 오류 발생 시 문제가 나타나는 XML 템플릿이나 UI부터 수정하기 쉬웠다. 그러나 해결 사례가 축적되면서 다음과 같은 순서가 더 효과적임을 확인했다.

1. **증상 고정:** 실패 장비, 당시 설정, 입력 프로젝트, 산출물을 가능한 한 동일 조건으로 확보한다.
2. **계층 분리:** 데이터 모델, 템플릿 생성, Automation Studio 설정, HW 등록, 현장 전장 중 어느 단계의 문제인지 나눈다.
3. **최소 재현:** 현장 전체 프로젝트가 아니라 해당 카드·모션·옵션만 포함한 재현 구성을 만든다.
4. **원인 확정:** 파일 비교만 하지 않고, 조건식 또는 출력 계약이 실제 기대와 어긋나는 지점을 찾는다.
5. **수정 범위 제한:** 템플릿, 직렬화 구조, 생성 조건, 설치 절차 중 실제 결함이 있는 경계만 고친다.
6. **반대 조건 테스트:** 성공해야 하는 경우와 실패하거나 생략돼야 하는 경우를 함께 검증한다.
7. **현장 결과 분리 기록:** 자동화 테스트 통과와 장비 재시험 완료를 따로 남긴다.

## 6. 결과: IOForge 개발로 얻은 엔지니어링 성과

### 확인 가능한 결과

- 드래그 앤 드롭 기반 카드·모션 구성과 HW/IO/CSV 동시 생성 도구를 구현했다.
- 2026-09-02 핵심 기능 배포 완료 기록이 있다.
- PS3300 지원과 인식 문제에서는 파일 생성 단계와 PLC HW 지원 등록 단계를 구분해 현장 정상 인식까지 추적한 이력이 있다.
- 물리 슬롯과 Node 구조, 0번부터의 Module No. 정렬, 속도 PDO 계약 등 생성 규칙을 개선했다.
- 2026-09~10월 레거시 표준의 옵션 유지·마이그레이션과 B&R Broadcast 생성 조건을 보완했다.
- 제공 Standard 및 주요 경계 조건의 회귀 테스트 코드를 추가해 재발 위험을 낮추는 기반을 만들었다.

### 아직 수치화하지 않은 결과

작업 시간 절감률, 현장 오조작 건수 감소, AS 요청 감소율 등은 체계적으로 측정한 수치가 없다. 그러므로 '몇 퍼센트 개선' 또는 '모든 오류 제거' 같은 정량적 주장은 하지 않는다. 현재는 **작업 흐름 자동화와 결함별 수정·검증 근거가 존재한다**는 수준으로 기술한다.
