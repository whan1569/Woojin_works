# IOForge 한계, 수용 근거와 발전 방향

## 1. 기본 판단

모든 프로그램은 목적과 운영환경에 따라 장점과 제약을 함께 가진다. IOForge는 범용 상용 서비스가 아니라 회사 내부 생산 현장의 IO 구성 업무를 단순화하기 위해 개발했다.

현재 핵심 생성 흐름은 기능적 완결 단계에 도달했으며, 장비별로 변하는 카드·신호·채널·Standard와 템플릿은 프로그램 코드가 아닌 사용자 관리 데이터로 분리했다. 따라서 새로운 장비 구성과 현장 예외가 발생해도 핵심 프로그램을 다시 개발하지 않고 대응할 수 있다.

## 2. Automation Studio 의존성

IOForge는 반복적인 카드·채널 구성과 XML·CSV 생성을 분리했지만 다음 작업까지 완전히 대체하지는 않는다.

- HW Upgrade 설치
- Additionally supported hardware 등록
- Automation Runtime Build
- 최종 설치 이미지 생성
- 실제 하드웨어 진단

이는 Automation Studio 전체를 재구현하지 않고 현장 작업자가 사용하는 범위를 최소화하기 위한 의도적인 경계다. 전문 설정과 최종 배포는 AS 담당자가 수행하고, 일반 사용자는 반복적인 구성 업무를 IOForge에서 처리한다.

### X20PS3300 사례

`ConfigHW.xml`과 `ConfigIO.xml`에는 X20PS3300이 정상적으로 포함돼 있었지만, CPU Configuration의 `Additionally supported hardware` 목록에는 누락돼 있었다.

그 결과:

- X20PS3300만 `not plugged`
- Serial Number·Firmware·Hardware Variant가 `-`
- X2X 버스가 통과해 뒤쪽 카드는 정상 인식

`Hardware.hw`를 비교한 결과 다른 동적 카드는 `AdditionalHardwareModule`과 버전으로 등록돼 있었고 PS3300만 누락된 것을 확인했다.

```xml
<Group ID="AdditionalHardwareEntry31" />
<Parameter ID="AdditionalHardwareModule31" Value="X20PS3300" />
<Parameter ID="AdditionalHardwareVersion31" Value="1.6.0.0" />
```

Automation Studio에서 다음 경로로 등록했다.

```text
Physical View
→ PLC Configuration
→ Additionally supported hardware
→ X20PS3300 / 1.6.0.0
```

이후 Clean Configuration, Rebuild와 Initial Installation을 수행해 실제 장비에서 정상 인식을 확인했다.

이 사례를 통해 동적 하드웨어 지원에는 다음 조건이 함께 필요하다는 것을 확인했다.

```text
동적 카드 구성
+ IO Mapping
+ HW Upgrade 사용 선언
= 정상 배포
```

## 3. 사용자 정의 데이터의 정확성

메타데이터와 템플릿이 잘못 등록되면 잘못된 산출물이 일관되게 생성될 수 있다. 이를 줄이기 위해 사용자를 분리했다.

| 사용자 | 대상 | 업무 범위 |
|---|---|---|
| 일반 사용자 | 생산공장·현장 작업자 | 프로젝트 구성, 카드 배치, 채널 설정, Standard 적용, 파일 생성 |
| Admin | AS·IO 구조 담당자 | 카드·신호·템플릿·Standard 등록과 수정 |

일반 사용자는 검증된 기준 데이터를 사용하고, 기술 기준을 변경하는 기능은 AS 담당자가 관리한다. 자유도는 사용자에게 제공하되 기술적 정합성은 프로그램과 관리 절차가 보완한다.

## 4. 로컬 우선 구조의 버전 차이

각 PC가 독립적으로 동작하므로 카드·신호·Standard 버전이 달라질 수 있다. 이는 다음 장점을 얻기 위해 수용한 제약이다.

- 인터넷과 중앙 서버 없이 사용
- 서버 장애 중에도 작업 지속
- 현장에서 즉시 예외 구성
- 중앙 변경을 기다리지 않고 문제 수습

공유 저장소 Push/Pull과 Standard 이력으로 차이를 완화하고, 향후 데이터 버전 표시와 승인본 비교 기능을 추가할 수 있다. 자동 동기화를 필수화해 로컬 독립성을 훼손하지는 않는다.

## 5. 현장 자유도와 표준 분기

현장별 예외를 허용하면 비슷한 프로젝트와 Standard가 늘어날 수 있다. 반대로 데이터가 부족한 상태에서 표준을 먼저 강제하면 신규 카드와 예외 구성 대응이 느려진다.

현재는 자유로운 프로젝트 구성을 허용하고 실제 데이터가 일정 규모에 도달한 뒤 반복 패턴을 Standard로 승격한다. 이는 표준화를 포기한 것이 아니라 표준의 근거를 확보하는 과정이다.

## 6. 파일 기반 저장

JSON·XML 중심 저장은 대규모 동시 편집과 실시간 중앙 분석에는 한계가 있다. 그러나 현재는 사용자 규모가 제한적이고 프로젝트별 작업이 독립적이며, 사람이 파일을 확인·백업·복구하기 쉽다. 별도 DB 서버가 필요하지 않고 기존 Automation Studio 파일 흐름과도 잘 맞는다.

중앙 분석이 필요한 규모에 도달하면 현재 파일 형식을 유지하면서 별도의 수집·분석 계층을 추가한다.

## 7. 사내 제한 배포

IOForge는 회사 내부 PC와 네트워크에서 제한 배포하며, 프로그램과 공유 저장소 접근은 기존 Windows·파일서버 권한을 사용한다.

일반 프로그램과 Admin의 분리는 외부 공격을 전제로 한 강한 보안 경계가 아니라 오조작 방지와 업무 범위 분리를 위한 운영 경계다. 현재 사용 범위에서는 상용 웹서비스 수준의 인증·암호화 체계를 추가하는 것보다 엔지니어링 데이터의 정확성 관리가 중요하다.

## 8. 실제 장비 검증

자동 생성과 정적 검사를 통과해도 Module ID, Serial Number, Hardware Variant, Firmware Version, ModuleOk와 X2X 상태는 실제 장비에서 최종 확인한다.

산업용 하드웨어의 Variant·펌웨어·베이스·배선 상태를 소프트웨어만으로 완전히 보장할 수 없으므로, 이를 프로그램 결함이 아닌 하드웨어 구성 도구의 검증 경계로 정의한다.

## 9. 신규 카드 등록 절차 보완

신규 카드는 XML 템플릿 등록만으로 완료된 것으로 판단하지 않는다.

1. 사용 AS 버전에 맞는 HW Upgrade 설치
2. IOForge 카드·채널 정보 등록
3. HW·IO 템플릿 등록
4. Additional Hardware 모델·버전 등록
5. 필수 Bus Module·Terminal 조합 확인
6. ConfigHW·ConfigIO·ModuleOk Mapping 검증
7. Clean/Rebuild 및 설치
8. 실제 장비의 ID·Variant·Firmware 확인

PS3300과 같은 증상이 발생하면 Additional Hardware 누락을 우선 확인하도록 매뉴얼과 프로그램 안내에 반영한다.

## 10. 발전 방향

### Stable Core, Configurable Edge

핵심 엔진은 안정적으로 유지하고 장비별 변동 요소는 Admin 관리 데이터로 확장한다.

- Stable Core: 프로젝트 편집, 검증, 저장, XML·CSV 생성, Push/Pull, 백업과 이력
- Configurable Edge: 카드, 신호, 템플릿, Standard, HW Upgrade 버전과 현장 예외

### 배포 의존성 검사

- 프로젝트 사용 카드와 `Hardware.hw` 비교
- Additional Hardware 누락 탐지
- HW Upgrade 버전 확인
- 필수 Base·Terminal 조합 검사
- 배포 가능·확인 필요 상태 표시

초기에는 파일을 자동 수정하지 않고 누락 카드, 요구 버전과 AS 설정 경로를 안내한다.

### 데이터 버전과 호환성 관리

- 카드·신호·Standard 데이터 버전 표시
- 생성 결과에 도구·데이터 버전 기록
- 카드·AS·HW Upgrade Compatibility Matrix
- Standard의 후보·승인·시험·폐기 상태 관리

### Configuration Mining

프로젝트가 충분히 쌓이면 카드 조합, 슬롯 배치, 공통 신호와 예외 패턴을 분석한다.

```text
프로젝트 축적
→ 반복 구성 탐색
→ Standard 후보 생성
→ AS 담당자 검토
→ 승인 Standard 승격
```

### 선택적 중앙 관리

향후 중앙 시스템은 현장 작업을 통제하는 필수 실행환경이 아니라 승인 Standard 배포, 검색, 이력과 통계 분석을 지원하는 선택적 계층으로 추가한다. 서버가 없어도 로컬 편집·생성·검증은 계속 가능해야 한다.

## 종합 판단

> IOForge는 모든 사용 사례를 중앙에서 통제하는 완전 자동화 시스템을 목표로 하지 않는다. 생산공장 사용자는 검증된 카드와 Standard로 복잡한 Automation Studio 작업 없이 프로젝트를 구성하고, AS 담당자는 Admin을 통해 기술 기준 데이터를 관리한다. 로컬 독립성과 빠른 현장 대응을 얻는 대신 버전 차이와 최종 장비 검증이라는 제약을 수용했으며, 이는 현재의 사내 운영환경과 사용자 역할을 고려한 의도적인 설계 선택이다.

완성형 프로그램은 모든 제약을 제거한 프로그램이 아니라, 사용 환경에서 중요한 문제를 해결하고 남은 제약을 통제 가능한 범위로 제한한 프로그램이다.
