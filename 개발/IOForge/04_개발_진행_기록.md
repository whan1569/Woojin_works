# IOForge 개발 진행 기록

## 1. 기간을 구분한 이유

IOForge는 개발 착수 당일 처음 문제를 접하고 만든 프로그램이 아니다. 개발 이전부터 현지·생산 현장 담당자와 지속적으로 소통하며 장비별 IO 구성, 카드 배열, 채널 관리 방식과 Automation Studio 작업의 불편을 수집했다.

따라서 전체 과정은 다음 두 기간으로 구분한다.

| 구분 | 기간 | 내용 |
|---|---|---|
| 사전 학습·정보수집 | 개발 착수 이전 ~ 2026-08-23 | 현장 소통, 기존 프로젝트와 IO 구성 분석, 반복 문제 축적 |
| 집중 구현·검증 | 2026-08-24 ~ 2026-08-27 | 요구 구조화, 프로그램 구현, 공유 기능, 실제 장비 시험과 문서화 |

5일 이내에 성과를 낼 수 있었던 이유는 문제를 단순화했기 때문이 아니라, 이전부터 축적된 현장 정보와 B&R 도메인 지식을 첫날 바로 구조화했기 때문이다.

> 정보수집에는 충분한 시간이 필요했으며, 축적된 정보를 프로그램 요구사항으로 정리하고 구현 방향을 결정하는 과정은 개발 착수 첫날 집중적으로 수행했다.

## 2. 사전 학습과 현장 정보수집

### 수집한 정보

- 장비별 실제 X20 카드 구성과 배열
- Powerlink Node와 Slot 구성 방식
- 카드 추가·교체 시 반복되는 작업
- 채널명·한글명·PLC 변수 관리 방식
- 기존 Standard와 실제 장비 구성의 차이
- `ConfigHW.xml`, `ConfigIO.xml`, CSV의 사용 흐름
- 담당자별 프로젝트 저장·전달 방식
- 현장에서 자주 발생하는 예외 구성
- 생산공장 사용자와 AS 담당자의 업무 범위 차이

### 현장 소통 방식

- 현지 담당자로부터 실제 카드 구성과 증상 전달
- Automation Studio와 System Diagnostics 화면 공유
- 생성 파일과 실제 장착 카드 비교
- 설정 변경 후 현지 재시험
- 시험 결과를 다시 공유받아 원인 범위 축소

이 과정을 통해 개별 불편을 다음과 같은 하나의 문제로 정리했다.

```text
Automation Studio 사용 난도
+ 반복적인 카드·채널 구성
+ 장비별 예외
+ 산출물 간 불일치 가능성
+ 프로젝트·Standard 자료 분산
= 현장 대응 지연과 AS 담당자 의존
```

### 확정 원인

다른 동적 카드는 `AdditionalHardwareModule`과 HW Upgrade 버전으로 선언돼 있었으나 X20PS3300만 누락돼 있었다.

```xml
<Group ID="AdditionalHardwareEntry31" />
<Parameter ID="AdditionalHardwareModule31" Value="X20PS3300" />
<Parameter ID="AdditionalHardwareVersion31" Value="1.6.0.0" />
```

### 해결과 현장 검증

```text
PLC Configuration
→ Additionally supported hardware
→ X20PS3300 / 1.6.0.0 추가
→ Clean Configuration
→ Rebuild
→ Initial Installation
→ 현지 장비 재시험
→ 정상 인식 확인
```

## 4. 개발 방식

이번 개발은 기능을 먼저 만든 뒤 현장에 전달하는 단방향 과정이 아니었다.

```text
현장 정보수집
→ 요구사항 구조화
→ 기능·설정 구현
→ 현지 적용
→ 결과 공유
→ 원인 범위 축소
→ 프로그램·매뉴얼 반영
```

현장 사용자의 실제 작업 순서를 기준으로 UI를 조정하고, 실제 장비 시험 결과를 생성 규칙과 운영 절차에 다시 반영했다. 이는 User-Centered Development와 Field-Driven Iteration을 결합한 방식이다.

## 6. 기간에 대한 최종 정리

> IOForge는 장기간의 현장 학습과 요구사항 수집을 바탕으로 개발했다. 2026년 8월 24일 축적된 정보를 프로그램 구조로 정리한 뒤, 8월 27일까지 5일 이내의 집중 구현·현지 피드백·실장 검증을 통해 핵심 기능과 운영 구조를 완성했다.

빠른 결과는 문제를 단순하게 본 결과가 아니라, 이전부터 축적한 B&R 프로젝트 경험과 현장 정보를 개발 착수 시점에 즉시 구조화할 수 있었기 때문에 가능했다.
