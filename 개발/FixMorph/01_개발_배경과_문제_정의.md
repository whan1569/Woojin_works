# FixMorph 개발 배경과 문제 정의

## 1. 개발 배경

구형 모니터를 신형 모니터로 교체하면 모니터 하드웨어뿐 아니라 운영체제, 런타임, 장비 프로그램과 데이터 구조도 함께 변경된다.

기존 장비의 FIX에는 시운전 과정에서 확정한 속도, 압력, 센서, 액추에이터, 보정값과 장비 옵션이 저장되어 있다. 이 값은 새 모니터에서도 보존해야 하지만, 구형 FIX 파일을 신형 프로그램에 그대로 적용하는 방식은 사용할 수 없었다.

FixMorph는 신형 모니터에서 생성한 FIX 구조를 유지하면서 기존 장비 FIX의 유효한 설정값을 옮기기 위해 개발했다.

## 2. 확인된 두 가지 문제

현장 적용 과정에서 문제를 크게 두 종류로 구분했다.

### 2.1 구형 FIX와 신형 FIX의 구조체 차이

구형 프로그램과 신형 프로그램의 FIX는 내부 구조체가 서로 다르다.

- 구조체 크기가 다를 수 있다.
- 신형에만 존재하는 필드가 있다.
- 같은 목적의 데이터라도 경로나 자료형이 달라질 수 있다.
- 신형 프로그램은 신형 구조와 체크섬을 기준으로 FIX 유효성을 판단한다.

따라서 구형 FIX의 값이 정상이어도 신형 프로그램에서는 목록 미표시, 불러오기 실패, `Default Fix-Data Loaded`, `Invalid Recipe Data` 등의 현상이 발생할 수 있다.

이 문제는 단순 파일 복사로 해결하지 않고 신형 FIX를 구조 기준으로 삼아야 한다.

### 2.2 카드 작업 이후 FIX 저장소 문제

카드를 구운 뒤에는 FIX 파일 변환과 별개로 FIX 저장소 문제가 남을 수 있다.

이 경우 FIX 파일만 다시 복사하거나 변환해도 저장 및 재부팅 문제가 해결되지 않는다. 확인된 대응 방법은 기존 파티션을 완전히 초기화한 뒤 소프트웨어를 새로 설치하는 것이다.

파티션 초기화와 신규 설치가 완료된 환경에서 신형 빈 FIX를 다시 생성한 후 FixMorph 변환을 진행해야 한다.

## 3. 두 문제의 구분

| 구분 | 문제 영역 | 대응 방법 |
|---|---|---|
| FIX 구조체 불일치 | 구형·신형 프로그램의 데이터 구조 | 신형 빈 FIX 구조에 구형 설정값 이식 |
| FIX 저장소 이상 | 카드 작업 후 파티션 및 설치 상태 | 파티션 완전 초기화 후 신규 설치 |

두 문제는 증상이 겹쳐 보일 수 있지만 해결 영역이 다르다. FixMorph는 구조체 불일치를 해결하는 도구이며, 저장소 문제는 설치 단계에서 먼저 정상화해야 한다.

## 4. 개발 목표

- 신형 FIX의 구조와 파일 형식을 유지한다.
- 구형 장비의 유효한 설정값을 보존한다.
- 신형 전용 필드와 하드웨어 매핑을 덮어쓰지 않는다.
- 변환 전후의 차이와 제외 항목을 작업자가 확인할 수 있게 한다.
- 원본 파일을 변경하지 않고 별도의 결과 파일을 생성한다.
- 변환 문제와 저장소 문제를 구분해 현장 대응 순서를 명확히 한다.
