# 장비 진단 기준 정립 및 TH 안정화 회고

## 1. 기존 진단 방식

기존에는 장비 이상 발생 시 다음 순서로 진단을 진행하였다.

```text
연결 검사 → 입출력 검사 → 논리 검사 → 코드 검사 → 연동 검사
```

각 단계의 목적은 다음과 같다.

| 단계     | 확인 내용                                         |
| ------ | --------------------------------------------- |
| 연결 검사  | 배선, 단자, 커넥터, 전원, 통신선 등 물리적 연결 상태 확인           |
| 입출력 검사 | 입력 신호가 PLC/HMI에 반영되는지, 출력 명령이 실제 장치로 전달되는지 확인 |
| 논리 검사  | 인터록, 알람 조건, 운전 허가 조건, 옵션 조건 확인                |
| 코드 검사  | 변수 매핑, 배열 인덱스, 상태 전이, 조건 분기, 예외 처리 확인         |
| 연동 검사  | 개별 동작이 전체 시퀀스 및 자동 운전 흐름에서 정상 연결되는지 확인        |

이 방식은 배선 불량, 센서 불량, 출력 누락, 인터록 조건 미충족, 코드 로직 오류를 추적하는 데 유효했다.

---

## 2. 이번 TH 안정화에서 확인한 점

이번 TH 안정화 작업에서도 먼저 기존 방식대로 연결 검사부터 진행하였다.

배선, 단자, 커넥터 상태를 확인했고, 점퍼 결선을 통해 일부 온도 입력이 HMI에 반영되는 것도 확인하였다.
또한 드라이 사이클 전 각 동작별 유닛 테스트를 진행하여 기본 동작 상태도 확인하였다.

즉, 다음 사항은 확인된 상태였다.

* 배선 자체가 완전히 잘못된 문제는 아님
* 일부 입력 경로는 정상 반영됨
* 기본 동작 및 일부 연동은 정상 확인됨
* 코드 흐름도 전체적으로는 동작 가능한 상태임
* 특정 AT 관련 모듈만 정상 연결되지 않는 문제가 남아 있음

이 과정을 통해 단순 배선 문제나 단순 코드 문제 가능성을 줄일 수 있었다.
결과적으로 남은 원인은 프로젝트 구성 또는 모듈 버전 정합성 문제일 가능성이 높다고 판단하였다.

---

## 3. 최종 원인

최종적으로 확인한 원인은 **AT 관련 하드웨어 모듈 버전 정합성 문제**였다.

실제 배선은 연결되어 있었고, 점퍼를 통한 입력 확인도 가능했지만, Automation Studio 프로젝트의 Hardware Configuration에서 사용하는 AT 관련 모듈 버전이 기존 TH 프로젝트 기준과 맞지 않았다.

이로 인해 실물 연결은 되어 있음에도 특정 모듈이 정상적으로 붙지 않는 문제가 발생하였다.

이번 사례를 통해 다음을 확인하였다.

> 물리적 연결이 정상이어도, 프로젝트의 Hardware Configuration과 모듈 버전이 실제 장비 기준과 맞지 않으면 모듈은 정상 동작하지 않을 수 있다.

---

## 4. 연결 검사와 버전 정합성 검사의 관계

이번 작업에서 중요한 점은 **연결 검사가 먼저 선행되어야 버전 정합성 검사도 의미가 있다**는 것이다.

연결이 되어야 다음 작업이 가능하다.

* 온라인 접속
* 모듈 상태 확인
* Hardware Configuration 비교
* Active Configuration 확인
* 커밋 및 다운로드 상태 확인
* 실제 장비와 프로젝트 설정 차이 추적
* 모듈 버전 변경 후 정상 반영 여부 확인

따라서 버전 정합성 검사는 연결 검사와 별개의 단계이지만, 순서상 연결 검사 이후에 수행되어야 한다.

정리하면 다음과 같다.

```text
연결이 안 됨 → 먼저 배선/통신/전원 확인
연결은 됨 → Configuration, 모듈 버전, Data Object 정합성 확인
```

---

## 5. 보완된 진단 순서

이번 경험을 통해 기존 진단 순서를 다음과 같이 보완한다.

```text
연결 검사
→ 하드웨어 / 버전 정합성 검사
→ 입출력 검사
→ 논리 검사
→ 코드 검사
→ 연동 검사
→ 실제 운전 테스트
```

가장 중요한 변화는 **연결 검사 이후 바로 입출력이나 코드로 들어가지 않고, 먼저 프로젝트 구성과 모듈 버전이 실제 장비와 맞는지 확인하는 단계**를 추가한 것이다.

---

## 6. 단계별 점검 기준

## 6.1 연결 검사

실제 장비의 물리적 연결 상태를 확인한다.

* 전원 공급 상태
* 단자 체결 상태
* 커넥터 체결 상태
* 센서 배선 상태
* 출력 배선 상태
* 접지 및 공통선 상태
* X2X, POWERLINK, Ethernet 등 통신 라인 상태
* 모듈 체결 상태

---

## 6.2 하드웨어 / 버전 정합성 검사

연결이 정상인데도 특정 모듈이 동작하지 않을 경우 반드시 확인한다.

| 항목                   | 확인 내용                                     |
| -------------------- | ----------------------------------------- |
| Active Configuration | 현재 활성화된 Configuration이 실제 대상 장비 기준인지 확인   |
| Physical View        | 실제 장착된 장비와 프로젝트 하드웨어 구성이 일치하는지 확인         |
| Controller / Panel   | PPC2100, PPC2200 등 대상 장비 설정 확인            |
| 하위 버스 구조             | X2X, POWERLINK, IF 구성 확인                  |
| 모듈 버전                | X20AT6402, X20AT2402 등 관련 모듈 버전 확인        |
| Library 버전           | 프로젝트와 라이브러리 호환성 확인                        |
| Data Object          | `arcfg_def` 등 동적 생성용 설정이 현재 대상 장비 기준인지 확인 |

이번 TH 안정화에서는 이 단계에서 AT 관련 모듈 버전 문제가 확인되었다.

---

## 6.3 입출력 검사

하드웨어 구성이 맞는 것을 확인한 뒤 실제 IO를 확인한다.

* 입력 신호가 PLC 변수에 반영되는지 확인
* HMI 표시값과 PLC 내부값이 일치하는지 확인
* 출력 명령 시 실제 DO가 발생하는지 확인
* 점퍼 테스트를 통해 입력 경로 확인
* 출력 LED 또는 전압 확인
* SSR, 릴레이, 밸브, 모터 등 실제 부하까지 신호 전달 확인

---

## 6.4 논리 검사

입출력 신호가 정상이라면 동작 조건을 확인한다.

* 운전 모드 조건
* 수동 / 자동 조건 차이
* 인터록 조건
* 알람 발생 및 해제 조건
* 옵션 사용 여부
* 온도존 활성화 여부
* 카드 타입 조건
* OLD / NEW 버전 분기 조건

---

## 6.5 코드 검사

논리 조건까지 맞는데 문제가 남아 있으면 코드 구조를 확인한다.

* 변수 매핑
* 배열 인덱스
* 카드 / 채널 분기
* 문자열 파싱
* 상태 머신 진행
* 중복 코드 경로
* 특정 조건 누락
* 예외 처리 누락

---

## 6.6 연동 검사

개별 기능이 전체 시퀀스에서 정상 연결되는지 확인한다.

* 개별 동작과 상위 시퀀스 연결
* 축 동작과 인터록 연결
* 입력 반응과 출력 명령 연결
* 알람 발생 시 정지 흐름
* 에러 리셋 후 재진입
* HMI 조작과 실제 동작 일치
* 자동 시퀀스 진입 가능 여부

---

## 6.7 실제 운전 테스트

마지막으로 실제 운전 기준에서 확인한다.

* 각 동작별 유닛 테스트
* 드라이 사이클 확인
* 공정 시간 반복 기록 확인
* 반복 운전 안정성 확인
* 알람 발생 여부 확인
* 온도 표시 안정성 확인
* 재부팅 후 설정 유지 여부 확인

---

## 7. 이번 작업에서 정립한 원칙

이번 TH 안정화 작업을 통해 다음 원칙을 정립하였다.

```text
1. 선이 맞아도 Configuration이 틀리면 모듈은 정상 동작하지 않을 수 있다.

2. 코드가 맞아도 모듈 버전이 틀리면 입력이 정상 반영되지 않을 수 있다.

3. 최신 버전이 항상 정답은 아니다.

4. 연결이 되어야 온라인 접속, 커밋, 모듈 상태 확인, 버전 추적이 가능하다.

5. 버전 문제는 처음부터 단정하는 것이 아니라, 연결·입출력·코드·연동 확인 후 남는 가능성으로 좁혀야 한다.

6. 실제 장비, Physical View, Configuration, Data Object, 모듈 버전, 코드가 함께 맞아야 정상 동작한다.
```

---

## 8. 최종 정리

이번 TH 안정화 작업에서는 기존 진단 절차를 통해 배선, 입출력, 코드, 연동 가능성을 순서대로 확인하였다.
그 결과 단순 배선 문제나 코드 문제 가능성을 줄일 수 있었고, 최종적으로 AT 관련 모듈 버전 정합성 문제를 원인으로 확인하였다.

이번 사례는 버전 문제를 우연히 찾은 것이 아니라, 기존 진단 절차를 충분히 수행했기 때문에 원인을 버전 정합성 문제로 좁힐 수 있었던 사례이다.

앞으로 장비 진단 시에는 다음 순서를 기준으로 한다.

```text
연결 검사
→ 하드웨어 / 버전 정합성 검사
→ 입출력 검사
→ 논리 검사
→ 코드 검사
→ 연동 검사
→ 실제 운전 테스트
```

최종적으로 이번 작업은 **최신 버전을 적용하는 것이 항상 정답이 아니라, 실제 장비와 프로젝트 코드가 함께 정상 동작하는 기준 구성을 찾고 관리하는 것이 더 중요하다**는 점을 확인한 작업이다.
