# 현장 대응 회고록 - 공개용

## 1. 개요

이번 현장 대응은 단순한 코드 수정이 아니라 장비 구조, 고객 공정 요구, 안전 조건, 시간 제약, 현장 커뮤니케이션을 함께 다뤄야 하는 작업이었다.

초기 요구는 특정 냉각수 출력이 원하는 시점에 동작하도록 수정하는 것이었다. 처음에는 최종 DO를 직접 제어하면 해결될 것처럼 보였지만, 실제 PLC Cyclic 구조에서는 해당 출력이 후단 로직에서 다시 갱신되기 때문에 단순 강제 출력으로는 요구 동작을 안정적으로 만들 수 없었다.

최종적으로 두 차례 대응을 통해 출력 소유 변수와 공정 조건을 다시 추적하고 정상 동작을 확인했다.

---

## 2. 현장 요구를 가설로 받아들이고 구조를 직접 확인

현장 담당자는 장비와 공정을 잘 이해하고 있었고, 요구 동작과 안전상 주의점을 구체적으로 설명했다.

현장 경험은 중요한 정보이지만 제어 프로그램 수정은 실제 출력과 안전 조건에 직접 영향을 주기 때문에, 전달받은 내용을 바로 코드로 옮기기보다 다음과 같이 접근했다.

```text
현장 요구사항
    ↓
실제 장비 동작 확인
    ↓
최종 I/O 확인
    ↓
해당 I/O를 소유하는 내부 변수 추적
    ↓
조건 / 인터록 확인
    ↓
수정 및 실제 장비 검증
```

즉, 현장의 설명은 빠르게 문제 범위를 좁히는 가설로 활용하고, 핵심 구조와 안전 조건은 직접 확인했다.

---

## 3. 최종 출력보다 출력의 소유 구조를 추적

초기에는 `DO_18_1`을 직접 ON 하는 방식이 검토되었다.

```c
if(MA_STAT.AbWaterFlow_Use)
{
    DO_18_1 = 1;
}
```

하지만 PLC Cyclic 내부에서는 특정 위치에서 DO 값을 변경하더라도 이후 출력 처리부에서 다른 변수에 의해 값이 다시 덮어써질 수 있다.

따라서 중요한 것은 `DO_18_1` 자체가 아니라 **최종적으로 이 출력을 결정하는 변수와 조건**이었다.

추적 결과 `DO_18_1`은 `DO_WaterFlow_Fixplate`의 상태를 통해 최종 결정되는 구조였고, 실제 수정 대상은 WaterFlow 관련 조건이었다.

```text
요구 동작
    ↓
DO_18_1
    ↓
최종 대입 위치 확인
    ↓
DO_WaterFlow_Fixplate
    ↓
WaterFlow 조건 / 공정 상태
```

이 경험을 통해 다음 기준을 다시 확인했다.

- DO를 직접 강제하기 전에 최종 출력 구조를 먼저 추적한다.
- 최종 출력보다 해당 출력을 소유하는 내부 변수를 찾는다.
- Cyclic 후반부에서 값이 다시 덮어써지는지 확인한다.
- 조건 분기와 안전 인터록을 함께 본다.
- 고객 요구를 코드 구조에 맞는 제어 조건으로 번역한다.

---

## 4. 서로 다른 전문성을 연결한 협업

현장 대응에서는 한 사람이 모든 정보를 가장 잘 알 수 없다.

- 현장 담당자: 실제 공정과 장비 사용 조건
- 장비 경험자: 기계 구조와 현장 운용 경험
- SW 담당자: 프로그램 상태, 조건 분기, I/O와 출력 흐름

이번 대응에서는 각 영역의 정보를 모은 뒤, 내가 코드와 출력 구조를 직접 추적해 하나의 원인 가설로 연결했다.

이 과정에서 중요한 것은 누가 맞고 틀리냐를 먼저 정하는 것이 아니라 **각자의 경험이 어느 지점에서 유효한지 구분하는 것**이었다.

---

## 5. 현장 신뢰는 설명보다 검증 결과에서 만들어짐

초기에는 이전 대응 이력 때문에 현장도 조심스러운 분위기였지만, 요구사항을 바로 반박하거나 단정하지 않고 실제 장비 상태를 함께 확인했다.

1차 대응에서 수정 방향을 잡고, 2차 대응에서 정상 동작까지 확인하면서 필요한 정보 공유도 더 원활해졌다.

이 경험에서 얻은 커뮤니케이션 기준은 다음과 같다.

- 상대의 설명은 우선 문제 해결을 위한 정보로 받아들인다.
- 안전과 핵심 구조는 직접 검증한다.
- 기술 용어보다 상대가 사용하는 공정 언어를 먼저 이해한다.
- 해결 결과와 확인 방법을 상대의 눈높이에 맞춰 설명한다.
- 의견 차이는 누가 맞는지보다 실제 상태와 결과로 좁힌다.

---

## 6. 현장 작업을 빠르게 만들기 위한 사전 준비

실제 현장에서는 코드 작성 시간보다 환경 설정, 빌드, 접속, 다운로드, 테스트에 더 많은 시간이 사용될 수 있다.

따라서 다음 항목을 사전에 준비하는 것이 효과적이었다.

```text
- 프로젝트 정상 빌드 여부
- 장비 접속 방식
- 관련 I/O Mapping
- 관련 변수 검색 결과
- 이전 변경 이력
- 예상 수정 후보
- 안전 / 인터록 조건
- 실패 시 원복 방법
- 테스트 순서
```

현장에서 처음부터 모든 것을 찾기보다 **사전에 좁힌 가설을 실제 장비에서 검증하는 형태**가 더 효율적이다.

---

## 7. 이번 경험에서 얻은 기준

### 기술
- 최종 DO는 결과이며 실제 수정 대상은 그 결과를 만드는 상태와 조건일 수 있다.
- PLC Cyclic에서는 앞에서 쓴 값이 뒤에서 다시 덮어써질 수 있으므로 최종 대입 경로를 봐야 한다.
- 소프트웨어 수정 전 실제 장비 출력과 안전 조건을 함께 확인한다.

### 협업
- 현장 경험자의 지식은 문제 범위를 빠르게 줄여주는 중요한 자원이다.
- 서로 다른 분야의 사람과 같은 문제를 논할 수 있어야 해결 속도가 빨라진다.
- 기술적 판단은 근거를 확인하되, 설명은 상대가 이해할 수 있는 언어로 전달한다.

### 실행
- 현장은 시간이 짧으므로 사전 준비와 원복 계획이 중요하다.
- 수정 자체보다 실제 장비에서 정상 동작을 확인하는 단계까지가 작업의 범위다.
- 작업 과정과 판단 근거를 기록하면 이후 유지보수와 재현 속도가 빨라진다.

---

## 8. 결론

이번 현장 대응에서 가장 중요한 경험은 **코드와 실제 장비 사이의 연결을 끝까지 추적하고, 서로 다른 전문성을 가진 사람들의 정보를 하나의 해결 과정으로 연결한 것**이었다.

최종 출력 주소만 수정하는 대신 내부 변수와 조건 구조를 추적했고, 현장의 공정 경험과 장비 경험을 활용하면서도 핵심 안전 조건은 직접 확인했다.

앞으로도 현장 문제는 다음 순서로 접근한다.

```text
요구를 듣는다.
↓
실제 상태를 확인한다.
↓
SW → I/O → 실제 장치 흐름을 추적한다.
↓
필요한 전문가와 원인을 논의한다.
↓
수정한다.
↓
실제 장비에서 검증한다.
↓
결과를 상대의 눈높이에 맞춰 전달한다.
```
